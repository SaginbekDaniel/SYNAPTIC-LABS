# NEXORA Transfer Protection

Демо для финтех-кейса Bank CenterCredit на ITU HACKATHON-2026. Клиент проверяет
планируемый перевод, выбирает предусмотренное сценарием действие, а аналитик
может открыть доказательства этой оценки.

## Локальный запуск

Запустите Docker с Compose и выполните команды из корня репозитория.

```bash
export NEXORA_TRANSFER_ANALYST_TOKEN="$(openssl rand -hex 32)"
docker compose up --build -d --wait
```

Откройте [NEXORA Transfer Protection](http://127.0.0.1:8080/lab/transfer-protection).
Для входа в расследование используйте значение переменной
`NEXORA_TRANSFER_ANALYST_TOKEN` из этой оболочки. При пустом значении доступ к
доказательствам закрыт. Клиентские проверки работают в обоих случаях.
Установите `NEXORA_TRANSFER_PROTECTION_ENABLED=false` и пересоздайте API, чтобы
все проверки возвращали `UNAVAILABLE / FEATURE_DISABLED`.

Для разработки используйте `make setup`, `make migrate`, `make api`, `make worker`
и `make web`. API, воркер и веб запускаются в отдельных терминалах. Настройте
PostgreSQL по [инструкции локальной разработки](development/local-setup.md).
Vite обслуживает экран на `http://127.0.0.1:5173/lab/transfer-protection`.

## Подготовка снимка и запрос

```text
Синтетический журнал + датированный контекст
  → фильтрация по occurred_at и known_at
  → существующий анализ графа и валидация доказательств
  → версионированный снимок получателя
  → справочник сценариев и выбор снимка на API
  → детерминированная политика → клиентский результат
                              → доказательства по токену аналитика
```

- `scripts/prepare_transfer_demo.py` готовит поставляемый каталог без HTTP-запросов.
  Cutoff обоих replay-сценариев зафиксирован в `transfer_demo.py`. Сборка начинает
  с фильтрации входов. Запись с точным временем допустима, если и `occurred_at`, и
  `known_at` не позже `as_of`. Для записи с точностью до дня дата должна
  предшествовать дню отсечения. Время для записи с точностью до дня не додумывается.
- `transfer_snapshot.py` вызывает существующий `run_analysis`. Сохраняются
  проверенные сигналы формаций, у которых получатель является субъектом,
  связи с транзакциями, ограничения покрытия, графовая политика и хэш
  конфигурации. Снимок получает ID по содержимому. Смоделированное намерение
  хранится только во входе политики и в базе или графе не появляется.
- API загружает каталог при запуске. Проверка использует справочник в памяти,
  сопоставляет сценарий и публичный псевдоним получателя, подставляет серверного
  отправителя и `as_of`. В пути запроса нет графового анализа, обращений к
  PostgreSQL или вызовов модели. Два запроса с одинаковым намерением, снимком и
  политикой дают одинаковый ID и решение.
- Аналитический запрос повторно вычисляет ID по входам и требует совпадения.
  Поле `ingested_at` существующего DTO означает `known_at` в этом каталоге.
  Опубликованная история оценок в MVP ограничена поставляемыми версиями снимков.

Следующие команды пересобирают снимки и типы API.

```bash
uv run python scripts/prepare_transfer_demo.py
make openapi
```

## Контракты

| Метод | Путь | Доступ |
|---|---|---|
| GET | `/api/v1/demo/transfer-checks/scenarios` | Список разрешённых сценариев и публичные реквизиты |
| POST | `/api/v1/demo/transfer-checks` | Проверка синтетического намерения по паре сценарий–получатель |
| POST | `/api/v1/demo/transfer-checks/evidence` | Точное намерение и ID оценки, заголовок `X-Nexora-Transfer-Analyst-Token` |

В развёртывании действует аутентификация шлюза. Следующий запрос проверяет сценарий `mule` через локальный шлюз.

```bash
curl --fail-with-body http://127.0.0.1:8080/api/v1/demo/transfer-checks \
  -H 'Content-Type: application/json' \
  --data '{"scenario_id":"mule","recipient_id":"recipient-mule","currency":"KZT","amount_minor":"15000000","client_context":"none"}'
```

API принимает KZT и положительную десятичную строку суммы в тиынах, до
38 цифр. Публичный результат содержит решение, код покрытия, причины,
допустимые действия, ID оценки, снимок и версию политики. Доказательства,
счета графа, временная шкала и контекст выдаются только по отдельному
токену аналитика длиной от 32 символов. Токен задаётся в окружении API,
сравнивается на сервере и передаётся через заголовок. Интерфейс очищает поле
после отправки и не сохраняет токен в URL или веб-хранилище. Ответы успешных
запросов получают `Cache-Control: no-store`. Для внешнего демо используйте
HTTPS и действующую аутентификацию шлюза.

## Политика transfer-protection-v1

1. Выключенный модуль, ошибка загрузки, несовместимая конфигурация графа или
   тайм-аут дают `UNAVAILABLE` с отдельным кодом причины. Тайм-аут в каталоге
   моделируется мгновенным ответом, а веб-клиент также ограничивает реальное
   ожидание запроса пятью секундами.
2. Отсутствующий профиль, истёкший срок действия, мало истории, неполный граф
   и неоднозначная хронология дают `LIMITED_SIGNAL` и риск `UNKNOWN`.
   Демопорог полноты истории составляет два наблюдаемых дня. Для
   неоднозначной хронологии учитываются вывод temporal flow и случаи,
   когда вся наблюдаемая история получателя имеет только точность до дня.
3. Структурный сигнал и подтверждённая хронология в одной формации дают
   `WARN`, если объяснение не покрывает доказательства этой формации и
   статистика сопоставимых счетов её не опровергает. Формации и сигналы из
   общего журнала не суммируются для `STEP_UP`.
4. При той же подтверждённой комбинации независимая запись из синтетического
   реестра инцидентов повышает решение до `STEP_UP`. Предупреждение по одной
   такой записи регулируется параметром `warn_with_confirmed_report_alone`
   в `configs/transfer_protection.toml`. Клиентское продолжение доступно для
   `ALLOW` и `WARN`. `STEP_UP` показывает требование симуляции, банковских
   проверок и операций система не выполняет.
5. При достаточном покрытии и отсутствии поддержанного основания результат
   `ALLOW`. Два наблюдавшихся в разные дни перевода от того же отправителя
   добавляют объяснение о знакомом получателе. Этот факт не снимает сигнал.
   Сумма и новизна получателя сами по себе не повышают решение.

Синтетический семейный контекст, зарплата, расчёты продавца и возвраты
учитываются только при совпадении получателя, времени доступности и ссылок на
все структурные и подтверждённые временные свидетельства формации.
Недоступная категория контекста остаётся неизвестной.

## Сценарии

| Сценарий | Ожидаемое и наблюдаемое решение | Основание |
|---|---|---|
| `regular` | `ALLOW` | Несколько переводов знакомому получателю |
| `mule` | `WARN` | Воронка и подтверждённый перевод дальше |
| `merchant` | `ALLOW` | Несколько поступлений и выплат с привязкой к реестру расчётов |
| `limited` | `LIMITED_SIGNAL` | Один наблюдаемый день |
| `review` | `STEP_UP` | Подтверждённая формация плюс отдельный реестр инцидентов |
| `replay_early` | `ALLOW` | Поздние данные ещё недоступны |
| `replay_late` | `STEP_UP` | Поздние операции и запись уже доступны |
| `timeout` | `UNAVAILABLE` | Моделируемый тайм-аут |

## Воспроизводимая оценка

```bash
uv run python scripts/run_transfer_protection_evaluation.py
```

Сводка выводится в терминал, JSON записывается в
`artifacts/transfer-protection-evaluation.json`. В отчёте указаны SHA Git,
признак изменений в рабочем дереве, версии и хэши входов, результаты по
сценариям и перцентили. Путь можно задать через `--output`.

`benchmarks/transfer_protection/holdout-v1.json` задаёт отдельную от каталога
демо выборку из 112 намерений, 67 легитимных и 45 мошеннических. Она фиксирует
состав, seed и порог amount-only в 200 000 KZT. Пороги политики не менялись
после первого прогона. Генератор получает рецепт и seed, а метка участвует
только в подсчёте метрик. Runtime API выборку и метки не загружает.

Все методы используют одинаковые намерения и cutoff. Amount-only
предупреждает по порогу суммы. First-time предупреждает при отсутствии
наблюдавшегося перевода между парой. Graph-only использует уровень
существующей политики открытия алертов `medium` и выше с учётом её
абстенций. Положительным исходом для расчёта матрицы считаются `WARN` и
`STEP_UP`. `LIMITED_SIGNAL` и `UNAVAILABLE` учитываются в знаменателе
и отдельно выводятся по статусам.

| Метод | TP | FP | TN | FN | Precision | Recall | FPR | FP / 1000 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Сумма | 15 | 36 | 31 | 30 | 29,41% | 33,33% | 53,73% | 537,3 |
| Первый получатель | 32 | 39 | 28 | 13 | 45,07% | 71,11% | 58,21% | 582,1 |
| Только граф | 31 | 32 | 35 | 14 | 49,21% | 68,89% | 47,76% | 477,6 |
| Transfer Protection | 29 | 5 | 62 | 16 | 85,29% | 64,44% | 7,46% | 74,6 |

Для полной политики 14 ответов из 112 имели `LIMITED_SIGNAL`, 4 из 112 —
`UNAVAILABLE`. На этой выборке политика сократила число ложных
вмешательств на 27 относительно graph-only и пропустила на два
мошеннических сценария больше. Пять ложных предупреждений пришлись на
легитимные сборы без данных о назначении. Рецепты повторяются, контекст и
отказы синтетические. Перцентили измеряют вычисление на готовом профиле
в процессе Python и исключают HTTP и подготовку графа.

## Проверки

Запускайте из корня проекта после `make setup`. Для pytest и Playwright
укажите отдельные базы по [инструкции тестирования](development/testing.md).

```bash
make lint typecheck test
make e2e
make iac-check
docker compose config --quiet
make smoke
```

Pytest проверяет доступность двух времён, детерминизм снимка, границы
данных, корректность матрицы ошибок и доступ к аналитическому API.
Playwright проходит пользовательские и аналитические действия на 1440 и
390 пикселях. Команда `make smoke` работает с запущенной сборкой через
шлюз на 8080.

## Трёхминутная демонстрация

- **0:00–0:40.** Откройте «Защита переводов». Проверьте регулярный перевод и
  продолжите в симуляции. Покажите легитимные расчёты продавца.
- **0:40–1:20.** Проверьте подозрительного получателя. Откройте реквизиты и
  покажите варианты отмены, обращения в банк и продолжения в симуляции.
  Выберите недостаточную историю и покажите отдельный статус.
- **1:20–2:25.** Проверьте сценарии позднего импорта в порядке ранней и
  повторной оценки. Из `STEP_UP` откройте расследование, введите токен,
  покажите время отсечения, снимок, граф и даты поступления данных.
- **2:25–3:00.** Покажите сводку holdout. Сравните 5 и 32 ложных вмешательства
  и 29 и 31 обнаруженных случая у полной политики и graph-only соответственно.

## Границы MVP

Общий демо-токен даёт право читать синтетические расследования этого
экземпляра. История защищённых банковских оценок потребует именных
ролей, авторизации на уровне клиента и хранилища неизменяемых версий снимков.
Графовый профиль готовится офлайн. Для подключения к реальному потоку
потребуются сроки обновления, наблюдаемость источников и процедуры
согласования с банком действий при сбоях. Экран использует русскую
локаль приложения. Общего каталога казахской локали в исходной ветке нет.
